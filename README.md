# Coding Agent Harness MVP

一个模型无关的本地实验台，用来回答一个具体问题：**给定一个支持 Tool Calling 的模型，它能不能在无人干预的条件下独立完成一个真实代码任务？**

用户只输入一次任务，模型在隔离副本中自主读取、修改、验证和修复，直到 Harness 判定成功或止损。是否成功由 Harness 判定，不采纳模型的自述。

这是个人实验项目，不是生产 IDE。以下记录的是八轮真实试跑中发现的问题、归因和工程调整——项目本身的价值主要在这部分。

---

## 为什么需要这样一个实验台

“会调用工具”不等于“能完成任务”。模型在单轮对话里能写出正确的函数，不代表它能在一个有测试、有依赖、有历史代码的工程里连续工作二十轮而不跑偏。

而这件事很难用常见的代码评测集回答：那些评测给定的是孤立函数和明确输入输出，判分靠字符串或单测比对。真实任务的难点在别处——模型要自己决定读哪个文件、改哪一行、什么时候该运行验证、验证失败后是修代码还是改测试。

所以需要一个能跑完整循环、并且能**独立判断结果真假**的环境。第二点比第一点难得多，也是这个项目踩坑最多的地方。

## 核心设计决策：成功判定权归 Harness

任务只有同时满足以下四个条件才记为成功：

1. Snapshot 检测到至少一个工程文件发生变化；
2. 最后一次文件变化之后执行了固定验证命令；
3. 验证未超时、未取消、无 Runner 错误，且退出码为 0；
4. 被修改的文件在验证期间没有发生未记录的外部变化。

模型输出“已完成”、没有产生变更、或改完没有重新验证，都不能进入成功状态。验证命令以参数数组执行、不经过 Shell，且不能被当前运行改写；测试和评估配置对模型只读。

这条规则看起来是常识，但它在第八轮仍然放过了一个完全跑不起来的产物。原因见下。

---

## 八轮试跑的失败归因

单一模型（MiniMax M3），单一任务：*“写一个小游戏网站，里面需要有 20 个童年游戏，其中一个是可在网页中直接玩的简化版我的世界。”*

| 轮 | 终止状态 | 现象 | 主因 | 工程调整 |
| --- | --- | --- | --- | --- |
| 1 | `repeated_tool_error` | 重构 `app.js` 时连续 3 次 `patch_invalid` 后熔断，15 Turn / 19.2 万 Token，未进入验证 | **Harness**：Patch 解析器对模型常见的无前导符空白行过严，且大文件只能走 Unified Diff | 空白行按原文当前位置区分上下文与新增；新增 `write_file` 支持整写与追加 |
| 2 | `model_service_error` | HTML、CSS、20 项清单均成功，生成 `app.js` 的请求在 185 秒后被上游网关返回 504，内部已重试 3 次 | **模型服务**；单次输出过大为放大因素 | 单次改动上限 12,000 字符并写入 Tool Schema `maxLength`；要求先建核心框架再分批追加 |
| 3 | `patch_conflict` | 分批生效，但模型把合法的 `window.Hub` 闭包外结构误判为无法访问注册器，3 次构造与最新文件不匹配的 hunk 后熔断，Prompt 累计 29.3 万 Token | **模型**误判触发，**Harness** 明显放大：append 不补换行、工具结果不反馈注册进度、Patch 只信任声明行号、历史大段写入反复进入上下文 | append 缺换行时自动补一个；写入后返回已注册/缺失游戏 ID 与架构合法提示；±100 行内旧上下文唯一匹配时自动重定位；已成功的大段参数在后续上下文中替换为哈希摘要 |

| 5 | `budget_exhausted` | 进度稳定从 5/20 增长到 20/20，首次进入固定验证，7 项过 5 项。更关键的是独立执行 `node --check` 发现记忆翻牌模块的边界写成了字面量 `\n` 而非换行符 | **模型**是语法错误的直接来源，**Harness** 反馈过晚：旧验收只检查字符串、清单和关键代码信号，从不解析 JavaScript | 每次修改 `.js` 后用 `node --check` 只解析不执行，诊断随工具结果返回；静态网站的最终验证必须先通过语法检查 |
| 6 | `repeated_tool_error` | 34 Turn、10 次辅助脚本运行、41 万 Token，工程修改 0 次。模型多次尝试一次调用完成写入并执行，旧工具忽略 `source` 参数；临时脚本达到 10 个上限后工具仍留在 Schema 中，连续 3 次同一错误被熔断 | **Harness** 接口摩擦：明知工具已不可用却仍暴露给模型，也不支持模型已反复表现出的调用方式 | `run_helper_script` 可选接收 `source`，单次完成写入与只读运行；第 11 个脚本自动淘汰最旧文件；每轮只发送当前状态真正可用的工具 Schema |

| 8 | **`success`（假阳性）** | 精确编辑与自动续批次最终驱动现场通过 JavaScript 语法检查和全部 7 项静态验收，Harness 判定成功。用户在预览中点击游戏，显示“游戏加载失败”；运行时复现为 **20/20 全部无法启动** | **Harness 假阳性**：核心框架与后续游戏模块混用了不同版本的 factory、HUD、stage、canvas 和 cleanup 接口。旧评估只检查源码信号和语法，从未执行真实入口 | 新增沙箱内逐游戏启动检查：逐个启动 manifest 中的游戏，启动异常或空白舞台会返回具体游戏 ID 并使验证失败 |

## 最贵的一课：第八轮

前七轮全是“模型或 Harness 没做完”，第八轮是“Harness 说做完了，其实没有”。

代价差别很大。前七轮的失败会立刻暴露，看一眼终止状态就知道要修什么。第八轮不会——它进入了 `success`，如果没有人手动点开那个预览，这个结果会被当作一次成功记录下来，进而支撑“模型能独立完成建站任务”的结论。

它躲过了两道门槛：七项静态验收检查源码里该有的信号（清单完整、注册调用存在、无占位词），`node --check` 保证代码能被解析。两道都通过，而产物一个都跑不起来——因为**能解析不等于能运行**，而所有检查都停在代码文本层面，没有一道真正执行入口。

修法不复杂：在只读沙箱里逐个启动 manifest 里的每款游戏，启动抛异常或舞台空白就失败，并返回具体是哪个游戏。难的是意识到需要这一步。

## 可迁移的几点结论

1. **验证必须执行真实入口。** 静态信号和语法检查都会放过“能解析但打不开”的产物。这一课出现在前七轮所有工程缺陷都修完之后，说明它不是初级疏漏，而是评估设计的默认盲区。

2. **多数“模型失败”其实是环境失败。** 八轮里主因归给模型的只有一轮，归给 Harness 的有五轮，模型服务一轮。如果不做分层归因，这些工具缺陷会被直接记成模型能力不足。所以每轮都按 **模型 / Harness / 环境 / 评估 / 预算** 五层分别判断，并明确写出“本轮不能得出什么结论”。

3. **工具形态要按模型适配，不能只给一套。** 同一个模型在 Unified Diff 上 9 次失败 5 次，换成基于唯一匹配的精确替换后失败率明显下降。工具协议的选择本身会影响成功率，这部分不该算进模型能力。

4. **熔断和预算是止损器，不是解决方案。** 四次熔断每次都“按设计正确触发”，但真正要改的始终是触发它的那个缺陷。靠放宽预算掩盖工具兼容问题，只会把同一个错误重复更多次。

5. **给模型看的上下文不能长得像源码。** 压缩占位符 `[HARNESS_COMPACTED ...]` 被模型当成项目代码抄进了产物。任何进入模型上下文的中间产物，都要假设它可能被原样写回文件。

---

## 当前边界

这部分需要明确，以免结论被外推：

- **样本量不足以评价模型能力。** 单模型、单任务族、八轮，只能用于发现 Harness 缺陷，不能得出任何模型完成率结论。
- **最终那次 20/20 启动通过，是 Harness 侧做了接口兼容修复之后的产物**，不能计作模型独立完成任务。
- **尚未完成一次全新工作区、无人工干预的正式重跑。** 当前现场跨越多个版本、累计超过 240 万 Token，只能用于验证恢复能力。
- 自动执行依赖 macOS `sandbox-exec`，不等同于容器或虚拟机隔离；其他系统只能用确认后执行。
- 从零建站只覆盖原生离线 HTML/CSS/JavaScript，不含后端和构建链。
- 逐游戏启动检查只覆盖首次启动、同步异常和空白舞台，不能替代持续操作、完整玩法和视觉的人工试玩。
- 固定验证通过只代表那组测试通过，仍需人工评审 Diff。

## 实现概要

单进程本地应用，Python 3.11+ 与 Streamlit。

| 模块 | 职责 |
| --- | --- |
| Task Orchestrator | 状态机、上下文投影、预算、工具循环与成功判定 |
| Model Adapter | 把具体模型 API 归一化为统一请求/响应；按模型分流工具集 |
| Tool Executor | 校验阶段、路径与参数，结构化返回错误，截断超长输出 |
| Workspace I/O | 枚举、搜索、读取、Patch、精确替换、哈希与 Diff |
| Validation Runner | 以参数数组运行固定命令，支持超时与终止 |
| Snapshot Manager | 建立任务起点、记录新文件、执行撤销 |
| Trace Writer | 将模型、工具、状态与用户事件写入本地脱敏 JSONL |

11 个结构化工具。自动执行始终操作源项目的工作副本，源项目不被修改；测试、配置与敏感路径对模型只读。辅助 Python 脚本可由模型临时创建，但只能读取隔离副本，不能写工程、联网或启动子进程。

预算：已有项目每批 20 Turn / 15 分钟，任务总计 60 Turn / 30 分钟 / 80 万 Token；从零建站每批 40 Turn / 30 分钟，总计 120 Turn / 60 分钟 / 200 万 Token。

工程状态：67 项确定性测试通过，`pip check` 无冲突。

## 运行

需要 Python 3.11 或更高版本。从零建站还需要 Node.js，用于 JavaScript 语法检查和受限运行时冒烟检查。

```bash
python3 --version          # 低于 3.11 时改用 python3.11 / 3.12 / 3.13
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip setuptools
python -m pip install -e '.[dev]'
streamlit run app.py
```

页面只绑定 `localhost`。Snapshot、Trace、辅助脚本与验证临时文件默认保存在 `~/.agent-harness/tasks/`。

接入任何兼容 OpenAI Chat Completions Tool Calling 的模型：

```bash
export AGENT_HARNESS_BASE_URL='https://example.com/v1'
export AGENT_HARNESS_API_KEY='your-key'
export AGENT_HARNESS_MODEL='your-model'
streamlit run app.py
```

也可以在页面侧边栏直接填写。API Key 不写入工作区、模型上下文或 Trace。注意项目文件、任务和工具结果会发送给所配置的模型服务，真实试验前需确认数据允许出域。

已有代码项目作为工作区时，根目录需要 `.agent-harness.json` 声明验证命令与路径权限：

```json
{
  "schema_version": 1,
  "validation_command": ["python", "-m", "pytest", "-q", "-p", "no:cacheprovider"],
  "validation_timeout_seconds": 30,
  "editable_paths": ["src"],
  "protected_paths": ["tests"],
  "sensitive_paths": [".git", ".env", ".venv"]
}
```

准备一个可直接试的 Fixture：

```bash
python scripts/prepare_fixture.py e01   # 或 e02
```

测试：

```bash
python -m pytest -q -p no:cacheprovider
```
