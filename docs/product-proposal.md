# 自主 Coding Agent Harness MVP 产品需求文档

| 项目 | 内容 |
| --- | --- |
| 版本 | MVP 首版（v1.0.0） |
| 状态 | 已补齐逐游戏启动验收，可进行全新无人工干预重跑 |
| 日期 | 2026-08-07 |
| 场景 | VibeCoding / 模型能力提升工程 |
| 产品形态 | 独立本地 Harness，不接 目标平台 |

## 1. 需求背景

目标模型已经具备多轮对话和工具调用能力，但“会调用工具”不等于“能独立完成代码任务”。算法提出进一步探索：用户只给一次任务，中间不干预，由模型自己决定如何读取、修改和验证；模型缺少分析工具时可以自己编写；甚至允许模型修改工程代码。

本期用一个独立 Harness 把该想法做成可运行、可观察、可评估的最小闭环，先判断方向是否成立，再决定是否接入目标模型和平台。

对应原规划：`2.3 Agent 能力（Loop/Workflow）`、`2.4 Tool 设计（文件、脚本和调用逻辑）`、`2.5 评估体系建设`，落地场景为 VibeCoding。

## 2. 产品定义

### 2.1 一句话定义

用户提交一项代码任务；对从零建站，Harness 自动创建项目与基础验收；对已有代码，用户选择项目。模型在隔离副本中自主完成“理解—修改—验证—修复”，Harness 只在满足客观成功标准后结束为成功。

### 2.2 目标用户

- 第一阶段：算法和 Agent 工程团队，用于模型能力实验；
- 第二阶段（本期不做）：在 目标平台上交付真实代码任务的用户。

### 2.3 核心假设

在固定任务、工具、预算和验证标准下，自主 Agent Loop 能让模型完成至少一类真实小型代码任务，并留下足以区分模型、Harness、环境和评估问题的记录。

## 3. MVP 目标与非目标

### 3.1 目标

1. 用户只提交一次任务，自动执行中不需要确认计划；
2. 模型能读取、搜索、修改工程并运行固定测试；
3. 测试失败后，模型能看到错误并继续修复；
4. 模型能编写临时辅助脚本解决项目内分析问题；
5. 模型可修改隔离副本中的工程代码，包括 Harness 源码；
6. 测试、权限、预算和成功条件不被模型改写；
7. 每次执行都能查看候选副本、Diff、验证结果和 Trace；
8. 通过仅供测试使用的确定性 Adapter 完成 Harness 工程验收，产品运行必须配置模型 API。
9. 从零建站时，用户无需手工创建工作区、配置和测试。
10. 网站产物可在页面内预览，并可下载为独立 ZIP。

### 3.2 非目标

- 不接入 目标平台、租户文件系统或用户账号；
- 不实现完整 Claude Code/OpenCode 产品；
- 不提供任意 Shell、联网搜索、在线安装依赖或 MCP 市场；
- 不自动覆盖源项目，不自动 Git 提交、合并或部署；
- 不证明目标模型或参考模型已经具备稳定的复杂 Coding 能力；
- 不以通过公开测试代替人工代码质量评审。

## 4. 用户故事

作为模型能力实验负责人，我希望给模型一个真实形态的代码任务后不再中途干预，让模型自己使用文件、Patch、验证和临时分析工具完成任务；结束后我可以看到它是否真正通过测试、修改了什么、为什么失败，从而判断下一轮应优化模型还是 Harness。

示例：

```text
用户注册时，空用户名没有返回错误。请定位并修复。
None、空字符串和只包含空白字符都应视为无效。
运行现有测试验证，不要修改无关功能，也不要修改测试。
```

## 5. 产品原则

1. 一次委托：自动执行过程中不设置计划确认点；
2. 结果可验证：模型不能靠文字宣布完成；
3. 控制面独立：模型可改工程，不能改当前 Run 的权限、预算和评估；
4. 默认不伤源项目：自主执行始终使用临时副本；
5. 全过程可追溯：工具、验证、状态和错误写入脱敏 Trace；
6. 失败有边界：任务不能成功时允许非成功终止，不无限消耗资源。

## 6. 核心流程

```text
选择“从零建站”或“已有项目”并输入任务
→ Harness 自动创建建站工作区，或校验已有项目
→ 复制隔离副本
→ 模型自主读取/搜索/可选计划
→ 修改代码或创建辅助分析脚本
→ 运行固定验证
→ 失败则回传错误并继续修复
→ 有变更且最新验证通过
→ 展示副本、Diff、验证结果和 Trace
```

异常分支：用户停止、预算耗尽、模型报告阻塞或系统错误时，以非成功状态保留现场。

## 7. 功能需求

### F01 已有项目选择与校验（P0）

- 当选择“使用已有代码项目”时，用户输入项目绝对路径；
- 项目根目录必须包含合法的 `.agent-harness.json`；
- 页面确认工作区有效；验证命令、超时、可编辑和只读范围默认折叠；
- 路径无效或验证命令不存在时，不允许启动任务。

验收：合法 Fixture 可以启动；主目录、根目录、缺少配置或配置错误的项目被拒绝。

### F02 运行模式（P0）

- 页面默认选择“自动执行”；
- 自动执行不等待计划批准；
- 保留“确认后执行”，用于计划确认场景；
- 任务开始后不能中途切换模式。

验收：相同 E01 在自动执行时不出现确认节点，在确认后执行时仍需用户确认计划。

### F03 隔离工程副本（P0）

- 自主任务启动时复制源项目到系统临时目录；
- `.git`、`.env`、`.venv`、缓存、依赖目录和配置的敏感路径不进入副本；
- 页面同时展示源项目和执行副本路径；
- 自主执行的任何工程修改仅发生在副本；
- 测试、项目配置和常见评估配置保持只读。

验收：任务成功后源项目字节不变，副本包含预期修改，敏感文件不在副本中。

### F04 自主 Agent Loop（P0）

- 模型每轮获得用户任务、运行策略、剩余预算、历史工具结果和当前真实可用的 Tool Schema（全集 11 个）；
- 模型自主选择读取、搜索、计划、修改、辅助脚本和验证顺序；
- `submit_plan` 为可选记录工具，成功后自动继续；
- 修改后必须重新验证；
- 单次代码修改参数最多 12,000 字符；10 个以上相似模块每批最多生成 2 个，避免超大模型响应；
- 长会话只保留近期工具轮次与确定性现场检查点，工具大文本给模型有界预览；
- 网站写入兼容 literal ID 与 `game.id`，返回已注册/缺失 ID、源码污染和追加架构提示；
- Harness 历史摘要不能写回源码，但允许模型删除旧版本已经泄漏的摘要行；
- 每次 JavaScript 修改后立即返回只读语法诊断；静态网站最终验证也必须通过语法解析；
- 多游戏网站使用统一 `window.GameHub` 与 factory 接口；最终验证逐个启动 manifest 中的游戏，拦截同步异常和空白舞台；
- MiniMax 使用 OpenCode 风格的 `edit_file` 精确替换，不向它暴露 Unified Diff；其他模型可继续使用 `apply_patch`；
- 连续 6 次只读分析时暂停辅助脚本，连续 10 次时下一轮只允许修改、验证或报告阻塞；
- 验证失败且仍有预算时，把结构化结果返回模型继续处理；
- 同一工具和同一参数连续出现 3 次时熔断。

验收：E01 可经历“修改—失败—再修改—成功”，且中间无人工操作。

### F05 自建辅助工具（P0）

- 模型可创建命名的 Python 辅助脚本；
- 单脚本最大 32 KB，每个 Task 最多保留 10 个、每个 Run 最多运行 10 次，单次最长 30 秒；
- 脚本只能读取隔离副本；
- 脚本不能写工程、读取敏感路径、联网或启动子进程；
- 脚本输出经长度限制和脱敏后返回模型；
- 工程修改仍必须通过受控的 `edit_file`、`apply_patch` 或 `write_file`，不能由辅助脚本直接写入。

验收：读取工程成功；写入、敏感读取、联网和子进程行为被沙箱拒绝。

### F06 工程代码开放修改（P0）

- 自动执行可修改工作副本中所有可见且未保护的工程文件；
- 包括被测 Harness 自身的 `src/`、应用入口、脚本和文档；
- 当前 Run 的 Orchestrator、Tool 权限、验证配置和预算由副本外控制，不因工程源码修改而变化；
- 局部修改使用模型适配的精确替换或 Unified Diff；新建、完整重写或分段追加大文件使用 `write_file`；三者遵守相同路径权限并记录改动文件。

验收：普通工程文件可修改；测试、配置和敏感路径修改被拒绝；修改 Harness 源码不增加当前 Run 权限。

### F07 独立验证与成功判定（P0）

- 验证命令由项目 Owner 预先配置，模型不可替换；
- 自主验证在沙箱中执行：读取副本、禁止网络、禁止写工程，只允许写 Task 专用临时目录；
- 成功必须同时满足：至少一个工程文件变化，且最后一次变化之后验证 exit code 为 0；
- 原项目测试本来通过但模型没有修改时，不能记为成功；
- 超时、停止、Runner 错误和非 0 exit code 均结构化返回。

验收：无改动时不误判成功；测试通过后进入 `success`；验证代码尝试写工程被拒绝。

### F08 预算与停止（P0）

- 已有项目单批次最多 20 Turn / 15 分钟，任务总上限 60 Turn / 30 分钟 / 80 万 Token；每批次最多运行 10 次辅助脚本；
- 单批次达到上限且已有成功代码变更时，在任务总预算内自动续批次；未产生变更时暂停避免空转；
- 用户随时可主动停止；
- 模型无法继续时可报告阻塞；
- 预算、阻塞、停止或系统错误均以非成功状态结束并保留 Diff/Trace；
- 用户可以带补充说明继续一个新的 Run，但不会把失败记为成功。

验收：各终止条件状态正确，停止后不继续接受晚到的模型写操作。

### F09 结果与追溯（P0）

- 主页面优先展示当前状态、执行时长和最新验证结果；
- 模型轮次、工具调用、辅助分析、Token 用量、模型、任务/批次 ID 和运行记录文件收入默认折叠的“运行详情”；
- 展示源项目、隔离副本、修改文件和 Unified Diff；
- 保存任务元数据、各 Run 的 JSONL Trace 和成功 Diff；
- 凭证和常见密钥字段必须脱敏；隐藏 reasoning 不落盘；
- 用户可以撤销副本中的 Agent 变更或开始新任务。

验收：算法可根据 Trace 区分模型输出、工具拒绝、验证环境和 Harness 状态问题。

### F10 一键从零建站（P0）

- 页面提供“从零创建网站”和“使用已有代码项目”双入口；
- 从零建站时不展示工作区路径和配置要求；
- 提交后自动生成空白项目、只读任务边界、结构化需求摘要和基础验收；
- 对“N 款游戏”和“我的世界”做确定性需求提取；
- 从零建站每批 40 Turn / 30 分钟，任务总上限 120 Turn / 60 分钟 / 200 万 Token，单次模型超时 120 秒；
- 产生 `index.html`/`styles.css`/`app.js` 后提供 iframe 预览；
- 可下载仅包含产品文件的 ZIP，不包含测试和 Harness 控制文件；
- 页面明确说明视觉和真实可玩性需人工验收。

验收：从零项目不含任何预制产品代码；确定性 Adapter 可从空目录创建网站并进入 `success`；页面可预览和导出。

## 8. 页面信息结构

任务前：

1. 执行方式；
2. 模型及 API 配置；
3. 项目来源；只有已有项目才展示路径和配置校验；
4. 代码/建站任务；
5. “开始创建网站”或“开始任务”。

任务中/后：

1. 当前状态、执行时长和验证结果；
2. 源项目与隔离副本；
3. 事件记录和可选模型计划；
4. 最新验证输出；
5. 修改文件和 Diff；
6. 停止、继续、撤销和新任务。
7. 网站任务的内嵌预览与 ZIP 下载。
8. 默认折叠的运行详情，包含模型轮次、工具调用、辅助分析、Token 用量、模型、任务/批次 ID 和运行记录文件。

MVP 不做聊天式逐步确认。自动执行中的用户输入只有初始任务；异常结束后的“继续”属于新批次控制，不是模型每一步询问用户。

## 9. 验收标准

### 9.1 工程验收

- 所有自动化测试通过；
- Streamlit 首页可加载，默认展示自动执行；
- 页面要求配置模型 API 后才能启动任务，且任务运行中不展示 API Key；
- 源项目不变、隔离副本修改、最终验证通过；
- 辅助脚本和验证沙箱越权用例被拒绝；
- 早期确认流程、停止、继续、Snapshot、Diff、撤销和 Trace 不回归。

### 9.2 方向验证（接目标模型后）

第一阶段使用 10～20 个小任务，每项至少重复 3 次，记录：

- 端到端任务通过率；
- 首次验证通过率和验证失败后的修复成功率；
- Tool 参数错误率、重复调用率和越权尝试率；
- Harness 误拒绝率、环境失败率；
- 人工 Diff 合格率；
- Turn、Token、主动执行耗时和辅助脚本使用情况。

当前 MVP 首版已完成自主 Harness、从零建站和逐游戏启动门槛的确定性工程验收。MiniMax 历史现场最终通过旧版语法与静态验收，但用户预览发现游戏接口混用，20 款游戏均无法正常启动；这属于 Harness 误判。当前产物经兼容修复后已通过 20/20 启动检查，Harness 也已把同一检查加入成功门槛。由于修复发生在模型结束之后，本轮不能计作 MiniMax 无人工干预成功；下一步仍需使用 MVP 首版和全新工作区原样重跑，目标模型试验尚未开始。

## 10. 风险与应对

| 风险 | 当前应对 | 剩余风险 |
| --- | --- | --- |
| 模型修改无关代码 | 任务约束、保护路径、Diff 和独立验证 | 测试无法覆盖所有业务语义 |
| 模型自写脚本越权 | 沙箱、无网络、无子进程、只读工程 | macOS 沙箱不等同生产隔离 |
| 模型修改 Harness 放大权限 | 控制面不从可修改副本热加载 | 下一 Run 采用前仍需人工审查 |
| 无限修复消耗 Token | 分批 Turn/时间、任务总 Turn/时间/Token 上限、重复熔断 | 大任务预算可能不足 |
| 验证本身有副作用 | 禁止写工程/联网，使用临时目录 | 未覆盖外部设备和所有系统调用 |
| 测试通过但实现不合格 | 逐游戏启动冒烟、强制展示 Diff，保留人工判断 | 仍不能覆盖持续操作、视觉质量和完整玩法 |
| 第三方模型数据出域 | 页面提示，仅用无敏感 Fixture 首测 | 需要正式数据合规规则 |

## 11. 依赖算法确认

接目标模型前需要算法提供或确认：

1. 目标模型 ID、版本、API/鉴权和 Tool Calling 协议；
2. 推荐 temperature、输出 Token、上下文窗口和超时；
3. System Prompt 是否叠加模型内置 Coding Prompt；
4. Tool Call/Result、stop reason、usage 和 reasoning 元数据样例；
5. 第一批固定任务及独立成功标准；
6. Trace 可保存字段和脱敏要求；
7. 是否接受本期“无网络、无安装、无任意 Shell”的自主工具边界。

## 12. 交付物与完成定义

交付物：可运行源码、11 个 Tool Schema、自主/审批两种模式、从零建站初始化、网站预览/导出、E01/E02 Fixture、自动化测试、产品 PRD、实现边界和验收记录。

本期完成定义：

```text
一次提交任务
→ 无审批自主执行
→ 可创建受限辅助脚本
→ 可修改隔离工程代码
→ 固定验证失败后继续修复
→ 有变更且验证通过才成功
→ 输出副本、Diff 与 Trace
→ 网站任务可直接预览并下载 ZIP
```
