## 3. MiniMax 首轮真实试跑

2026-08-06 使用 MiniMax M3 执行“20 个童年游戏，其中包含可直接游玩的简化版我的世界”。模型成功读取任务与验收，并创建 `index.html`、`styles.css`、20 项 `game-manifest.json` 和首版 `app.js`；随后在重构 `app.js` 时，连续提交了 3 个含无前导符空白行的非标准 Unified Diff，旧解析器均返回 `patch_invalid`，熔断器按设计暂停。

该 Run 在首次 `run_validation` 前结束，因此不能判断网站任务是否完成，也不能据此判定 MiniMax Coding 能力不达标。主因归为 Harness 格式兼容，模型输出非标准 Diff 是触发条件，大文件生成方式是放大因素。详细记录见 [MiniMax 首轮建站试跑与归因](./history/minimax-zero-code-run-20260806.md)。

### 第二轮（2026-08-07）

MiniMax 使用新 `write_file` 成功创建 HTML、约 11.7 KB CSS 和 20 项游戏清单，证明首轮 Patch 阻塞已解除。随后生成 `app.js` 的模型请求在内部最多 3 次服务尝试后返回 HTTP 504。该结果主归因模型服务超时，超大单次输出为放大因素；仍未进入固定验收。详见 [第二轮 504 归因](./history/minimax-zero-code-run-20260807.md)。

### 第三轮（2026-08-07）

MiniMax 成功创建核心框架并分批追加游戏，证明 504 分块调整生效；但它将合法的 `window.Hub` 闭包外游戏模块误判为不可访问，三次构造与最新文件不匹配的 Patch 后熔断。运行累计 Prompt 292,815 Token，暴露历史大写入内容反复进入上下文的问题。详见 [第三轮 Patch Conflict 归因](./history/minimax-zero-code-run-20260807-patch-conflict.md)。

### 第四轮（2026-08-07）

续跑在 399.638 秒内用满 40 Turn，本 Run 使用 770,670 Token，未进入固定验证。实际已有 5/20 个游戏，但旧进度规则持续返回 0/20；旧历史压缩摘要还被复制进 `app.js`。预算正常止损，主因属于 Harness 进度识别和上下文投影。详见 [第四轮预算耗尽归因](./history/minimax-zero-code-run-20260807-budget-exhausted.md)。

### 第五轮（2026-08-07）

进度从 5/20 稳定增长至 20/20，并首次运行固定验证：7 项通过 5 项。失败包括旧任务 literal ID 规则和源码中的“占位”注释；随后又由 `node --check` 发现旧验收未覆盖的真实 JavaScript 语法错误。详见 [第五轮固定验证失败归因](./history/minimax-zero-code-run-20260807-validation-failed.md)。

### 第六轮（2026-08-07）

续跑使用 34 Turn 和 10 次辅助脚本运行，但没有修改工程或重新验证。模型达到 10 个临时脚本上限后，连续三次创建新脚本而被熔断；本 Run 实际消耗 411,365 Token。该结果归因于辅助工具接口摩擦、静态工具暴露和旧任务热更新不完整，不是项目验证结论。详见 [第六轮辅助脚本熔断归因](./history/minimax-zero-code-run-20260807-helper-loop.md)。

### 第七轮（2026-08-07）

续跑用满 40 Turn，本 Run 消耗 722,599 Token。共调用 12 次读取、7 次搜索、11 次辅助脚本和 9 次 Patch；Patch 中 4 次成功、5 次失败。JavaScript 语法错误被推进到文件末尾，但仍未修复完成。该轮证明诊断反馈有效，也确认 MiniMax 与 Unified Diff 接口不匹配、分析过多和手动续批次是当前主要 Harness 摩擦。详见 [第七轮编辑循环归因](./history/minimax-zero-code-run-20260807-edit-loop.md)。

### 后续自动续跑与预览缺口（2026-08-07）

v0.3.7 的精确编辑和自动续批次最终驱动当前现场通过 JavaScript 语法与 7 项静态验收，Harness 因此进入 `success`。但用户在网页预览中点击游戏后看到“游戏加载失败”。运行时复现显示 20/20 均无法启动：核心框架和后续游戏模块混用了不同版本的 factory、HUD、stage、canvas 与 cleanup 接口。

这不是 iframe 预览故障，而是旧评估只检查源码信号和语法，未执行真实入口，属于 Harness 假阳性。MVP 首版统一了当前产物的兼容接口，并新增沙箱内逐游戏启动检查。修复后的当前产物通过 20/20 启动检查和原 7 项静态验收。由于兼容修复由 Harness 开发侧完成，本次不能计作 MiniMax 独立完成任务。

## 4. 成功判定

任务只有同时满足下列条件才记为成功：

1. Snapshot 检测到至少一个工程文件变化；
2. 最后一次工程变化之后执行了固定验证；
3. 验证未超时、未取消、无 Runner 错误且 exit code 为 0；
4. 修改文件在验证期间没有发生未记录的外部变化。

模型只输出“已完成”、没有修改、或修改后未重新验证，都不能成功。

## 5. 当前边界

- 自主沙箱当前依赖 macOS `sandbox-exec`；
- 只对 Python + pytest Fixture 形成确定性结果；
- 没有自动合并隔离副本到源项目；
- 不允许辅助脚本联网、在线安装工具或任意 Shell；
- 从零建站当前只覆盖原生离线 HTML/CSS/JavaScript，不含后端和构建链；
- 自动验收只覆盖首次启动、同步异常和空白舞台，不能代替持续操作、完整玩法与视觉人工试玩；
- 测试通过不代表代码必然符合所有业务要求；
- 尚不能得出目标模型完成率或能力提升结论。

## 6. 下一个验收节点

使用 MVP 首版和全新工作区原样重跑，不复用当前已人工修复的现场。正式模型成功必须在无人工改码条件下同时通过 JavaScript 语法、逐游戏启动、固定 pytest，并接受人工玩法抽查。
