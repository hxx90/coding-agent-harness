# 从零建站（MVP 首版）：产品流程与验收边界

## 1. 用户体验

从零建站不再要求用户事先创建代码目录、`.agent-harness.json` 或测试。用户只需：

1. 选择“从零创建网站”；
2. 配置 MiniMax/目标模型等真实模型；
3. 用自然语言输入任务；
4. 点击“开始创建网站”；
5. 结束后检查预览、Diff 和验证，下载 ZIP。

## 2. Harness 自动完成的事

提交时，Harness 会创建一个不含产品代码的临时源项目，仅包含：

| 文件 | 作用 | 模型权限 |
| --- | --- | --- |
| `.agent-harness.json` | 验证命令、保护和敏感路径 | 只读 |
| `TASK.md` | 用户任务与静态建站边界 | 只读 |
| `site-requirements.json` | Harness 可确定提取的验收信号 | 只读 |
| `tests/test_site_acceptance.py` | 独立基础验收 | 只读 |

项目初始不包含 `index.html`、`styles.css`、`app.js` 或游戏实现，所以仍是 0→1 任务。之后按自主模式再创建隔离副本，模型只修改该副本。

## 3. 需求提取的 MVP 范围

MVP 首版不用第二个模型自由生成验收，只做可解释的确定性提取：

- 识别“N 个/款/种游戏”，将 N 写入只读需求文件；
- 任务出现“我的世界”时，要求游戏清单包含它；
- “我的世界”按原创简化方块沙盒验收，不复刻官方 3D 产品；
- 默认离线运行，不使用 CDN、外部素材和后端；
- 要求本地 `index.html`、`styles.css` 和 `app.js`。

未被规则明确识别的主观要求不会被假装成可自动判定的指标。

## 4. 自动验收能判断什么

- 必需入口文件存在；
- HTML 引用本地 CSS/JS，含移动端 viewport 和语义主区域；
- 不引用外部 URL，不含常见占位文案；
- CSS 含响应式、键盘焦点和减少动画处理；
- JavaScript 有基础交互；
- 游戏 manifest 数量、唯一 ID、玩法/控制字段和注册实现；
- “我的世界”有 Canvas、地形、破坏/放置、快捷栏和本地保存的代码信号。
- 多游戏网站中 manifest 的每款游戏都能通过统一大厅入口启动，且首次启动没有同步异常或空白舞台。

## 5. 自动验收不能判断什么

- 页面是否真正好看；
- 每款游戏是否好玩，或进入后经过持续操作才出现的运行时 Bug；
- 规则是否符合某个用户对“童年游戏”的主观理解；
- 所有屏幕尺寸和浏览器下的真实体验；
- 通过字符串匹配的代码是否真正完整实现逻辑。

因此，Harness 的 `success` 代表“代码变更 + 独立基础验收通过”；产品端到端成功还需要用户通过内嵌预览完成人工检查。

## 6. 输出与安全

- 预览把生成的 HTML/CSS/JS 内联后放在 Streamlit 组件 iframe 中；
- ZIP 只包含可编辑产品文件，不包含测试、Harness 配置或需求控制文件；
- 单文件仍受 1 MB 上限约束，导出产物最大 25 MB；
- 建站任务每批 40 Turn / 30 分钟，任务总上限 120 Turn / 60 分钟 / 200 万 Token，单次模型超时 120 秒；
- MiniMax 或其他外部模型会接收任务、文件和工具结果，不应输入公司敏感信息。

## 7. 实现文件

| 文件 | 职责 |
| --- | --- |
| `project_bootstrap.py` | 需求提取、空白工作区、任务边界与基础验收 |
| `javascript.py`、`website_runtime_smoke.js` | JavaScript 语法检查与逐游戏启动冒烟检查 |
| `website_output.py` | 内联预览和仅产品文件 ZIP 导出 |
| `app.py` | 从零/已有项目双入口、模型配置、预览与下载 |

## 8. 大文件生成可靠性

- 新建或完整重写文件时，模型可使用 `write_file` 的 `replace` 模式；
- 大型 `app.js` 可分段使用 `append` 模式，避免生成脆弱的超大 Unified Diff；
- MiniMax 的局部修改使用 `edit_file` 精确替换，适合超长行和语法修复；其他模型可继续使用 `apply_patch`；
- 两种写入方式共用相同的可编辑/保护/敏感路径检查、1 MB 单文件上限、Snapshot、Diff 和撤销机制；
- 任何写入后仍必须运行固定验证，工具写入成功不等于任务成功。
- 单次 `edit_file.old_string/new_string`、`write_file.content` 或 `apply_patch.patch` 分别最多 12,000 字符；
- 单批次有成功代码变更时，Harness 在总预算内自动续批次；无变更时暂停避免空转；
- 10 个以上相似模块必须分批生成，每批最多 2 个；20 游戏任务会在受保护的 `TASK.md` 中明确该规则；
- 模型服务 5xx/429/连接错误最多自动尝试 3 次；三次仍失败后暂停，避免无上限等待和重复计费。
- append 自动补齐缺失的块间换行；多游戏网站统一通过 `window.GameHub` 暴露 `registerGame/get/list`，所有 factory 使用同一接口，后续批次作为独立模块追加在核心闭包之后；
- 每次写入 `app.js` 后返回 `registered_ids`、`missing_ids` 和下一步建议，literal ID 与 `game.id` 均可识别；
- 长会话参考 OpenCode 只保留近期 6 个 Assistant 工具轮次和确定性现场检查点；工具大文本只给模型有界预览，完整事实仍保留在 Trace；
- 历史摘要和裁剪提示不得写入源码，工具层会拒绝新增此类内容，并允许删除旧版已泄漏摘要行。
- 每次修改 `.js` 后用 Node.js `--check` 只解析、不执行项目代码，并把诊断立即返回模型；最终验证还会在拒绝联网和写文件的 macOS 沙箱中逐个启动游戏。
