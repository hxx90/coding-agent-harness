# MiniMax 第七轮：编辑循环与批次上限归因

## 1. 结论

本轮不是任务失败结论。MiniMax 在保留的 20 游戏现场上产生了 4 次有效代码修改，JavaScript 语法错误位置从约 1015 行逐步后移到文件末尾，证明语法诊断能驱动修复。但它仍使用 Unified Diff，9 次 Patch 中有 5 次因格式、冲突或无变化失败；并且用满 40 Turn 后需要用户再次手动续跑。

主因归为 Harness 与 MiniMax 的编辑接口适配不足，以及只有“单批次预算”而没有“自动续批次 + 任务总上限”。模型过度读取和 Patch 构造不稳定是触发与放大因素。

## 3. v0.3.7 调整

1. **MiniMax 精确编辑适配**：参考 OpenCode 的模型分流思路，MiniMax 使用 `edit_file(old_string, new_string)`，不再接收 `apply_patch`；该工具支持超长行、唯一匹配检查、Snapshot、Diff、权限校验和 JavaScript 语法诊断。
2. **无进展动作保护**：连续 6 次成功只读分析时暂停辅助脚本；连续 10 次时，下一轮只提供修改、验证或阻塞报告工具。
3. **自动续批次**：单批次达到上限且已有成功代码变更时，Harness 自动创建下一 Run，工作区、历史、Snapshot 和任务不变。
4. **任务级止损**：建站任务总上限为 120 Turn / 60 分钟 / 200 万 Token。若单批次没有任何成功变更，仍暂停以避免空转。

## 4. 验收边界

v0.3.7 的 63 项确定性测试已全部通过，其中新增长行精确编辑、MiniMax 工具分流、无进展动作保护、自动续批次和任务总上限回归。

当前保留现场可用于验证“精确编辑能否修复旧语法债务”，但它已跨越多个 Harness 版本并累计超过 240 万 Token，不能作为正式模型评估样本。恢复验证后，仍需使用 v0.3.7 全新工作区完成一次无人工干预的同任务重跑。
