# Robo 硬件 Harness：黄金场景与改造方案

状态：本地 MVP 已实现；这些场景继续作为实体硬件阶段的验收目标

这里不再罗列底层单元测试，而是用少量真实用户任务反推 Robo 必须具备的能力。

本文把“Anthropic 提出的协议”理解为模型上下文协议 MCP。MCP 适合做设备能力发现、工具调用、状态资源读取和远程接入，但不能替代实时控制器、硬件看门狗或物理急停。

协议依据见：[MCP 用于 Robo 多型号机械臂接入的协议研究](research/anthropic-mcp-for-robo-hardware-harness.md)。本文以当前稳定的 `2026-07-28` 无状态规范为准，协议事实和 Robo 的设计推论在研究记录中分别标明。

## 一、我们真正要做的产品

Robo 不是一个“能发串口命令的聊天机器人”，而是一个硬件 Coding Agent：

1. 读懂机器人项目、驱动和厂商 SDK；
2. 接入机械臂、夹爪、相机及传感器；
3. 构建、运行并观察当前代码；
4. 根据日志、遥测和物理结果定位问题；
5. 修改代码，在模拟器中验证，再安全部署到设备；
6. 经用户批准后执行真实任务，失败时停止、回放和恢复。

也就是说，Robo 的闭环应是：

```text
用户目标
  ↓
理解代码与设备能力
  ↓
修改代码 → 构建 → 模拟验证
  ↓
部署到设备 → 小范围试运行
  ↓
观察日志 + 遥测 + 相机 + 安全状态
  ↓
继续修改 / 完成任务 / 回滚
```

## 二、多型号机械臂如何接入

建议让 Robo 充当 MCP 主机，每个机器人工作单元或边缘电脑运行一个统一的“Robo 设备网关”MCP Server。网关内部再通过 Adapter 连接不同厂商，而不是让 Agent 直接学习每个厂商的串口、ROS Topic 或 SDK。一个 Robo Host 可以通过独立 MCP Client 连接多个网关。

```text
Robo CLI / App Server（MCP 主机）
              │
       MCP：发现、资源、工具
              │
       Robo 设备网关 MCP Server
              │
     HardwareRuntime（安全与执行权）
        ┌─────┼─────┬─────┐
      UR     Franka   xArm   模拟器
    Adapter  Adapter Adapter Adapter
```

每接入一种新机械臂，只新增两样东西：

- 一份设备描述：型号、自由度、坐标系、能力、单位、限制、固件和安全要求；
- 一个厂商 Adapter：把统一能力翻译成厂商 SDK、ROS 2、串口或网络协议。

上层只认识少量统一能力，例如关节运动、笛卡尔运动、夹爪、相机、力传感、停止和回零。不同机械臂缺少某项能力时，Robo 必须调整计划或明确拒绝，不能猜测。

MCP 在这里负责：

- 用 Resources 暴露设备描述、当前状态、遥测摘要、运行记录和部署版本；
- 用 Tools 暴露连接、校准、观察、执行技能、部署、停止和诊断；
- 用 Prompts 提供厂商推荐的调试、校准和故障恢复流程；
- 用 stdio 连接本机网关，用 Streamable HTTP 连接机器人边缘电脑。

设备的自由度、负载、夹爪、坐标系和安全限制属于 Robo 自己的版本化设备能力清单，不属于 MCP 的协议 capability。Resource 变更通知只负责提醒 Host 重新读取摘要，不能当高频遥测总线。

真正的速度环、轨迹插补、租约、限位、碰撞保护、看门狗和急停仍由 `HardwareRuntime` 及设备控制器负责。MCP cancellation 和 Tasks cancellation 都只是协作式取消，不证明电机已经停止；即使 MCP 连接断开，机器人也必须自行进入安全状态。

## 三、六个黄金场景

### 场景 1：第一次接入一台陌生机械臂

用户说：

> 这是刚买的机械臂和它的 Python SDK，帮我把它接到 Robo，确认相机、夹爪和六个关节都能工作。

Robo 应该：

1. 阅读当前仓库、SDK 示例和设备文档；
2. 发现设备并读取型号、固件、关节和传感器能力；
3. 生成或补全该型号的 Adapter 与设备描述；
4. 先连接模拟器或伪设备，通过统一契约测试；
5. 连接真机，只执行读取状态、低速单关节、夹爪开合和停止测试；
6. 保存校准结果和一份“该型号已经接通”的运行记录。

Harness 要补：设备网关、Adapter 开发包、能力描述、驱动契约测试、校准流程，以及从厂商错误码到统一故障的映射。

本地经典验收：准备两个行为不同的假厂商 SDK；Robo 为它们加载不同 Adapter，但上层用完全相同的命令完成发现、连接、读取关节和停止。

### 场景 2：让机械臂叠衣服

用户说：

> 帮我调通这台机械臂，让它把桌上的这堆衣服叠完。

Robo 应该把目标拆成一个持续观察的闭环，而不是一次生成整段轨迹：

1. 检查机械臂、夹爪、RGB-D 相机和工作空间是否已校准；
2. 观察衣物类别、边缘、抓取点和桌面障碍；
3. 选择或生成“展开—对齐—折叠—放置”技能；
4. 在模拟器或数字孪生中预演，展示碰撞、速度和力限制；
5. 用户批准后，只执行当前一步；
6. 每一步后重新看相机和力传感器，根据衣物是否滑落、抓空或折偏来重规划；
7. 无法确认时停止并让用户处理，而不是继续猜。

Harness 要补：多模态观测、坐标系和标定、可组合机器人技能、步骤级审批、长任务状态、失败恢复，以及“计划目标”和“真实结果”的比较器。

本地经典验收不应一开始就挑战“一堆任意衣服”。第一版用固定相机和一条毛巾：Robo 能在模拟环境完成两次抓取和一次对折，任何一步抓空都停止并重新观察。混合衣物堆应作为后续能力。

### 场景 3：观察正在运行的代码并自动修复

用户说：

> 机械臂总是转过头，帮我观察它现在跑的代码，找出问题，修好后再试一次。

Robo 应该同时看到三层信息：

- 代码层：当前 Git 提交、未提交改动、配置、依赖和启动命令；
- 软件层：构建结果、进程状态、标准输出、错误日志、调用耗时和异常；
- 物理层：目标关节角、实际关节角、轨迹、力、电流、相机画面和安全事件。

三层数据必须用同一个 `run_id` 关联。Robo 才能判断“代码发出了 90，但驱动按弧度解释”这种问题，而不是只读日志猜测。

修改流程必须是：停止并解除武装 → 在隔离工作树修改 Adapter → 运行测试和录制回放 → 模拟器验证 → 构建带版本号的产物 → 部署 → 10% 速度试运行 → 比较修改前后结果 → 接受或自动回滚。

Harness 要补：运行观察器、代码版本与设备 Trace 关联、进程管理、构建/部署/重启、健康检查、试运行和回滚。禁止在机械臂运动时热改安全代码。

本地经典验收：在伪机械臂驱动中放入“角度/弧度转换错误”。Robo 从目标值与实际轨迹的 Trace 定位到转换代码，修改后通过回放和模拟器，再部署到本地子进程；新轨迹正确，失败时恢复旧版本。

### 场景 4：同一个任务换一台机械臂

用户说：

> 昨天用 Franka 跑通了抓取，今天换成 xArm，尽量不要重写任务。

Robo 应该先比较能力，而不是比较品牌：自由度、负载、工作空间、夹爪、控制模式、坐标系和安全限制。任务使用统一的“移动到位姿、抓取、释放、观察”能力；只有 Adapter 和设备描述发生变化。

如果新设备能力不足，例如没有力控或够不到目标，Robo 应明确指出差异并修改任务策略，而不是把旧轨迹直接下发。

Harness 要补：能力协商、设备描述版本、任务与设备的兼容性检查，以及 Adapter 一致性测试。

本地经典验收：同一抓放任务在“7 自由度带力控”和“6 自由度无力控”两个模拟 Adapter 上运行；前者使用接触检测，后者自动选择视觉确认或明确拒绝需要力控的步骤。

### 场景 5：机械臂、相机和传送带协同

用户说：

> 相机看到衣服到位后，让机械臂抓起来叠好，最后放到右侧传送带。

Robo 应该把多个设备组成能力图，统一处理时间、坐标系、控制权和故障传播。相机事件可以触发计划，但不能直接绕过机械臂审批；传送带和机械臂进入共享区域时必须互斥。

Harness 要补：多设备拓扑、时钟同步、坐标变换、跨设备租约、事件条件、并发调度和事务式停止。

本地经典验收：三个模拟设备同时运行；相机发出物体到位事件后机械臂抓取，机械臂离开共享区后传送带才启动。任一设备超时，另外两台进入预先定义的安全状态。

### 场景 6：现场失败、复现和安全恢复

用户说：

> 刚才抓取到一半机械臂断线了，查清楚发生了什么，别让它直接继续。

Robo 应该先把状态标记为“物理状态未知”，使旧租约和武装状态失效；如果通信恢复，先读取真实关节和联锁状态，再决定是否能安全停止。完整保存代码版本、部署版本、命令、ACK、日志、遥测和相机关键帧。

开发者可以在没有真机时回放这次事故，注入相同断线点，修改代码后比较新旧行为。只有人工确认现场安全并重新武装，任务才能继续。

Harness 要补：事故包、确定性回放、故障注入、状态恢复流程、带外急停和安全证据记录。

本地经典验收：在固定轨迹的第 3 步断开伪设备。第一次运行生成事故包；修改重连逻辑后离线回放，验证不会自动续跑；重新连接仍需人工确认和重新武装。

## 四、需要改造 Harness 的六个深模块

| 深模块 | 小接口负责什么 | 隐藏的复杂性 |
| --- | --- | --- |
| 设备接入模块 | 发现、描述、连接设备 | MCP、厂商 SDK、ROS 2、串口、网络、版本和能力差异 |
| 硬件运行模块 | 执行、观察、停止 | 队列、租约、ACK、限位、看门狗、状态机和并发 |
| 运行观察模块 | 打开一次 `run_id` 的统一时间线 | Git 版本、OpenTelemetry 数据、进程日志、命令、遥测、图像、指标和安全事件 |
| 构建部署模块 | 构建、部署、试运行、回滚 | 本机/边缘电脑、环境、产物、进程重启、健康检查和版本切换 |
| 任务技能模块 | 运行可观察、可暂停、可恢复的机器人技能 | 感知、规划、步骤状态、重新观察和恢复策略 |
| 安全监督模块 | 武装、审批、停止、恢复 | 策略、联锁、物理状态未知、人工确认和所有设备的最终仲裁 |

现有代码可以复用文件读取/修改、Shell、MCP 工具发现、会话、审批和 App Server Effect。代码扫描显示当前 MCP 接入仍以旧式初始化、`tools/list` 和 `tools/call` 为主，并保留了已弃用的 Sampling。主要缺口是新旧 MCP 版本适配、`server/discover`、Resources/订阅、硬件领域模型、设备运行状态、代码到设备的部署闭环，以及把 OpenTelemetry Trace 展示给用户的硬件 UI。新硬件实现不再依赖已经弃用的 MCP Sampling 和 Logging。

## 五、推荐的第一条实现路线

不要直接从“叠完一堆衣服”开工，它同时要求困难的视觉、柔性物体建模和灵巧控制，无法判断失败来自 Harness 还是算法。

推荐按三个可演示里程碑推进：

1. **接入闭环**：两个假厂商机械臂都能通过统一网关完成发现、连接、读取、低速运动和停止；
2. **自修复闭环**：制造角度/弧度 Bug，Robo 能观察 Trace、修改 Adapter、回放验证、部署和回滚；
3. **任务闭环**：固定相机下让模拟机械臂折一条毛巾，按步骤观察、执行和失败恢复。

这三条通过后，再接第一台真实机械臂，并逐步从固定毛巾扩展到不同衣物和整堆衣服。

## 六、本轮需要确认

开始实现前只需要确认四件事：

1. Anthropic 协议按 MCP 理解；
2. 采用“Robo 设备网关 + 厂商 Adapter”，而不是每种机械臂给 Agent 一套专用工具；
3. 第一批实现按“接入闭环 → 自修复闭环 → 单条毛巾任务”推进；
4. MCP 只负责接入和上下文，实时控制与安全始终留在 `HardwareRuntime`。
